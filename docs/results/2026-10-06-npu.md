# NPU exports on two phones, 2026-10-06

What ExecuServe does with Qualcomm (QNN) and MediaTek (NeuroPilot) NPU exports, how that was
tested on a Snapdragon 8 Elite Gen 5 and a Dimensity, and what came out. The files this page
rests on are in [2026-10-06-npu/](2026-10-06-npu/), captured when they ran.

## What changed, and why

- **One runtime with four delegates.** ExecuTorch publishes its Android library per delegate
  (`executorch-android-vulkan`, `-qnn`) and none with MediaTek; an app can link only one. The
  app now ships ExecuTorch 1.5.1 built from source by [`tools/executorch`](../../tools/executorch):
  XNNPACK, Vulkan and QNN in `libexecutorch.so`, and MediaTek's runtime beside it
  (`libexecutorch_pd_jni.so`, OpenWeights' NPU-prefill/CPU-decode runner ported to 1.5.1).
- **Qualcomm's runner had to be patched to serve.** Through the stock Android library it
  ignores `stop()` (so `max_tokens` and stop strings cannot end a reply), ignores `reset()`
  (every conversation continues the last one's positions), aborts the process when the window
  fills, has no text `prefill`, and is told every model is Llama 3 (wrong stop tokens for
  Qwen3). [`patch_qnn.py`](../../tools/executorch/patch_qnn.py) fixes all five.
- **Each phone is offered its own chip's NPU files.** The catalog lists `qnn/<soc>` and
  `mtk/<soc>` only when Android's `Build.SOC_MODEL` names that chip and the NPU runtime loads,
  and only when the export's `config.json` agrees about the chip. Installs record their backend,
  and `/v1/models` reports `executorch-qnn` or `executorch-neuropilot`.
- **Qualcomm's HTP drivers ship with the app**, from `qnn-runtime` 2.39: the first release
  with the Hexagon V81 (8 Elite Gen 5) skeleton. 2.37, the version ExecuTorch 1.5.1 pins,
  stops at V79. The app also declares `libcdsprpc.so`; without it Android 12+ keeps the
  driver from reaching the DSP and the runner fails to load with no message.
- **A MediaTek install is several files**: the compiled chunks, the embedding table, the CPU
  build of the same window (which decodes) and the tokenizer, each checked against its
  published digest.

## Results

### Snapdragon 8 Elite Gen 5 (QDC, SM8850, Android 16, 24 GB)

The export: Qwen3-1.7B at a 4,096-token window, compiled with QAIRT 2.37 for SM8850 on a Modal
x86 host (81 min, 81.5 GB peak RSS), structural check passed. It loads and answers on the NPU
through ExecuServe: correct answers ("The capital of Japan is Tokyo."), `max_tokens` ends a
reply (`length`), a repeated question after another conversation gets the identical answer from
the same 24 prompt tokens (reset works), streaming works.

Speed, all through ExecuServe's run history (`/v1/execuserve/runs?format=csv`), Qwen3-1.7B at
4k on all three, greedy, three runs each, thermal status none, on AC power. Each run is a fresh
conversation: the short prompt is "Explain how a refrigerator keeps food cold. /no_think"
(128 out), the long one is the 702-token passage of the 2026-10-04 report (64 out).

| | CPU (XNNPACK, GPTQ) | GPU (Vulkan) | NPU (QNN HTP) |
|---|---:|---:|---:|
| 21-token prompt: prefill, tok/s | 296, 300, 309 | 323, 356, 368 | 253, 284, 292 |
| 21-token prompt: decode, tok/s | **54.2, 54.5, 54.7** | 42.0, 42.1, 42.6 | 24.7, 24.8, 24.9 |
| ~700-token prompt: prefill, tok/s | 330, 344, 367 | 645, 702, 730 | **1,708, 1,717, 1,725** |
| ~700-token prompt: decode, tok/s | 33.4, 33.5, 34.5 | 33.7, 36.8, 36.9 | 24.6, 24.6, 24.8 |
| Time to the first token, long prompt | about 2.0 s | about 1.0 s | **about 0.41 s** |

So the NPU reads a long prompt five times faster than the CPU and two and a half times faster
than the GPU, and decodes at half the CPU's rate on a short exchange. Its graphs are compiled
for the whole 4,096-token window and attend over all of it on every step, where XNNPACK's cost
grows with the position actually reached.

How to read the table:

- **Same harness, same definitions.** Prefill is the time to the first token; decode rates
  exclude that token (`(completion − 1) / decode_ms`).
- **The long prompt is 702 tokens on CPU and GPU and 697 on the NPU.** The generic runner
  takes long prompts in pieces and tokenizes each, which adds a token at each piece's edge; the
  QNN runner prefills in its own 128-token blocks, so it gets the whole prompt (a first build
  that fed it pieces prefilled at 1,180 tok/s, which is why it no longer does).
- **Quantization differs.** CPU and GPU: 8-bit dynamic activations, 4-bit weights. NPU:
  ExecuTorch's Qwen3-1.7B recipe, 16-bit activations, 4-bit weights in blocks of 16, an 8-bit
  output layer and KV cache.
- **The 21-token prefill row is overhead, not throughput**, and the NPU pads every prompt to a
  128-token block.
- **Not measured: power.** The QDC phone sits at 100% on AC.
- ExecuTorch's own Qualcomm runner (`qnn_llama_runner`, built from 1.5.1), given the same token
  ids, prefilled the long prompt at 2,100 to 2,190 tok/s and decoded at 26 to 31: ExecuServe's
  HTTP, tokenizer and callbacks cost about a fifth of the prefill rate here
  ([observer lines](2026-10-06-npu/sm8850-reference-runner-observer.txt)).

### Dimensity (POCO X8 Pro Max, MT6991, 12 GB)

- **LFM2.5-1.2B-Instruct, MediaTek 2k**: loads and answers on the NPU through ExecuServe:
  correct answers, `length` at `max_tokens`, identical answers after a reset. The NPU prefills,
  the cache is handed to the CPU in 0.07 ms, and the CPU decodes at 39 to 43 tok/s.
- **Qwen3 at 4k does not fit this phone.** Qwen3-1.7B's load drew available memory from 7.4 GB
  to 0.8 GB within six seconds and the system killed it; Qwen3-0.6B loaded, then left 0.77 GB
  free and was killed on its first request. Most of that memory is outside the process (the
  Neuron backend's KV and IO buffers, sized to the window, and its weight imports). The runtime
  now hands off all-attention models like Qwen3 as well as LFM2 (it builds Qwen3's 28 layer
  mappings), but no Qwen3 answer has been produced through MediaTek yet.

## Fixed along the way

- A model whose load got the process killed was loaded again at every service restart, which
  killed it again: the restart now skips the model whose load did not finish, and waits for a
  request (`HostPlatform.loading`).
- A load failure now carries ExecuTorch's last log lines; "Failed to load model runner" said
  nothing.
- `tools/execuserve pull` waited forever on MediaTek exports (it looked for an install named
  after the first chunk) and showed 0 MB throughout; it now finds the install and shows the
  folder's size.
- An install's size now counts every model file, so a MediaTek install is not reported as its
  CPU half.

### The final build, on a fresh session

The SM8850 was wiped between QDC sessions; the final build (with the QA fixes below) was
installed fresh, the NPU file copied in with its manifest, and the CPU build pulled by the
phone. `/v1/models` reports `executorch-qnn` with the alias `qwen3-1.7b-qnn`; the behavioural
checks pass again; the benchmark repeats at 1,640 to 1,734 tok/s prefill on the 697-token
prompt and 21.5 to 26.5 tok/s decode
([run history](2026-10-06-npu/sm8850-execuserve-qnn-final-runs.csv)).

In the app's own Chat tab, the same meeting notes (about 170 tokens) answered on the NPU in
3.29 s (prefill 1,098 tok/s, decode 26.5) and on the CPU in 3.00 s (377 and 42.8): the NPU
starts answering about three times sooner and the CPU then streams faster, so on a short prompt
the two finish together. The recordings are `marketing/ad/assets/clips/npu-sm8850-chat.mp4`
and `cpu-sm8850-chat.mp4`, each with a JSON beside it giving the prompt and the reply.

Recording it surfaced one more bug: the Android Chat showed a bold span's raw `**` until its
closing pair arrived. It now closes an open span while a reply streams, as the browser chat
already did.

## Adversarial QA

Codex (`gpt-6.1-sol`, medium, read-only) reviewed how the backends are shown, with the Library
screenshots from the SM8850. Fixed from it:

- **A model whose load or first request gets the process killed is marked failed**, not
  retried: every native open, prefill and generate leaves a record (`NativeCrashGuard`) that a
  restart reads. Verified on the POCO: Qwen3-1.7B's MediaTek build was loaded on purpose, the
  system killed the app, and the restarted service listed it as failed ("The app was stopped
  while this model was running, most likely because the phone ran out of memory") while LFM2.5
  loaded beside it; the Library offers **Try again**.
- **MediaTek failures are reported as failures.** A failed CPU decode step used to return a
  truncated reply as finished; the runtime now returns an error, refuses a prompt past its NPU
  window as `context_length_exceeded`, and stops decoding when the window is full.
- **Every catalog row and installed model says which processor runs it** (CPU, GPU, NPU
  (Qualcomm), NPU (MediaTek) prefill with CPU decode), whether or not its export names a
  quantization; MediaTek rows show the whole install's size and a memory caution.
- **NPU install ids always name their backend**, QNN builds get a short alias like the others
  (`qwen3-1.7b-qnn`), and the browser chat shows a model's id where two installs share an alias.
- **An NPU `.pte` copied in by hand is refused**, with how to install it, instead of opening on
  the CPU runner and being reported as `executorch-xnnpack`.
- QNN refusals are recognized in prefill and generate, not only at load; refusal messages no
  longer promise that a CPU build "runs anywhere".

Left for later: run records and the CSV do not yet carry the backend; the thread setting does not
reach MediaTek's CPU decode; `tools/execuserve pull` does not see a download the app refused;
and a phone whose NPU is unsupported gets no explanation of why no NPU rows appear.
