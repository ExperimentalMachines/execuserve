# GPU (Vulkan) exports on three phones, 2026-10-04

What ExecuServe does with Vulkan exports, how that was tested on a Mali and two Adreno GPUs,
and what came out. One model throughout: Qwen3-0.6B at a 2,048-token window from
`experimentalmachines/Qwen3-0.6B-ExecuTorch`, `vulkan/Qwen3-0.6B-vulkan-8da4w-2k.pte` for the
GPU and `xnnpack/Qwen3-0.6B-8da4w-gptq-2k.pte` for the CPU. The engine-level study, with the
same phones run through OpenWeights' engine and ExecuTorch's own runner, is OpenWeights'
[docs/research/vulkan-on-device.md](https://github.com/ExperimentalMachines/openweights/blob/main/docs/research/vulkan-on-device.md).
The files this page rests on are in [2026-10-04-vulkan/](2026-10-04-vulkan/); each says at
its top whether it was captured when it ran or transcribed afterwards from the session's
terminal output, and keys are redacted.

## What changed, and why

- **One runtime library for both delegates.** The app ships
  `org.pytorch:executorch-android-vulkan:1.5.1`, which links XNNPACK and Vulkan; the plain
  `executorch-android` AAR links XNNPACK only, and a Vulkan `.pte` cannot load on it. 1.5.1
  because the exporter moved to it the same day, and ExecuTorch promises older files load on
  the next minor runtime, not newer ones (`1f75829`).
- **GPU exports are listed only where they can run** (`c67ec10`). `VulkanSupport` offers the
  `vulkan/` folder when Android reports Vulkan 1.1 and no refusal is on record. A refusal is
  recorded only from the runtime's own words (a shader needing a feature the driver lacks,
  no usable Vulkan device), at load or first run, and kept per runtime release. A bad file,
  a full window or running out of GPU memory never costs the phone its GPU builds. On a
  refusal the error names the way out: the same model's CPU build.
- **The server reports the delegate** (`13085b1`, then `f46833d`). `/v1/models` says
  `executorch-vulkan` or `executorch-xnnpack`. On the SM8650 the first build said
  `executorch-xnnpack` for the GPU file, because it reported only the runtime; each install's
  `execuserve.json` now records `"backend"`. A file copied in by hand, and an install whose
  manifest predates the field, have no record and fall back to the installed id's name.
- **A refusal reaches the screen and the download queue at once** (`f46833d`). The Models
  screen collects a `StateFlow`, and the downloader checks for a refusal when a download is
  queued and again when it starts, for the screen and `tools/execuserve pull` alike.
- **CPU and GPU installs never share a folder.** GPU install ids always contain `vulkan`
  and CPU ids never do; a CPU file named for Vulkan is not listed. `pull vulkan/x.pte`
  takes exactly that path.
- **Only the runner's two overflow messages mean a full window.** The Android wrapper appends
  the runtime's recent log to its exceptions, and that log mentions `max_context_len` on every
  run, so the old match turned GPU failures into "context full".

## Results

| Phone | Build | What was checked | Result |
|---|---|---|---|
| POCO X8 Pro Max, MT6991, Mali-G925 | debug at `13085b1`, timing at `57a292f` | `/v1/models`, chat, stream; `tools/compat` suites | `executorch-vulkan`; Tokyo, Jupiter, a correct stream; OpenAI SDK 16/16, edge cases 28/28, Anthropic SDK 8/8 (tools, streaming, reasoning, Responses chaining, eight concurrent requests) |
| QDC Snapdragon 8 Gen 3 (SM8650), Adreno 750 | debug at `c67ec10` | Serve the GPU build | Tokyo; `/v1/models` said `executorch-xnnpack`, fixed in `13085b1` |
| QDC Snapdragon 8 Elite Gen 5 (SM8850) | **release APK** 0.1.0 (24) at `f46833d` | Catalog pulls of both builds on the phone, records, answers, stream, timing | Each build in its own folder, recorded as `vulkan` / `xnnpack` and reported so; greedy Tokyo, 51, Jupiter on the GPU; a stream of 36 `data:` lines ending in `[DONE]`; the server's totals then said 5 completed, 0 failed; later, 12 timed requests, all `stop` |

Speed on the SM8850, from the server's run history (`/v1/execuserve/runs?format=csv`), greedy,
7 threads, thermal status none, three runs each:

| | CPU (XNNPACK, GPTQ) | GPU (Vulkan) |
|---|---:|---:|
| 27-token prompt: prefill, tok/s | 540, 900, 931 | 794, 871, 900 |
| 27-token prompt: decode, tok/s | **123.1, 124.8, 127.5** | 80.9, 90.8, 92.5 |
| 702-token prompt: prefill, tok/s | 746, 749, 771 | **901, 1,007, 1,180** |
| 702-token prompt: decode, tok/s | 49.6, 50.4, 51.4 | **61.3, 61.7, 63.9** |

So on this phone the GPU is the better choice for long prompts and long conversations, and
the CPU for short exchanges.

The same twelve requests on the POCO (debug build at `57a292f`, because the phone's
Play-signed release cannot be updated with the upload-key build without deleting its data;
sent from the Mac through `adb forward`; unplugged, thermal status 0):

| | CPU (XNNPACK, GPTQ) | GPU (Vulkan) |
|---|---:|---:|
| 27-token prompt: prefill, tok/s | 197, 380, 391 | 173, 178, 189 |
| 27-token prompt: decode, tok/s | **56.4, 59.3, 59.5** | 15.3, 15.8, 16.3 |
| 702-token prompt: prefill, tok/s | 325, 328, 335 | **371, 431, 432** |
| 702-token prompt: decode, tok/s | **29.7, 29.9, 30.4** | 13.3, 13.5, 13.6 |

On the POCO's Mali-G925 the GPU only reads the long prompt faster (1.1 to 1.3 times, slowest
to fastest of the three runs), and the CPU decodes 2.2 to 3.9 times faster at both measured
lengths, so for this model the CPU build is the one to serve there. Other Mali GPUs and
larger models were not measured. The catalog
lists both and does not yet recommend one.

## What was not recorded at the time

The SM8850's first session's run history was empty after the server restarted, so its speed
table is a second measurement on the same phone, captured to the CSV when it ran. The POCO's
table was measured afterwards for the same comparison, also captured. The
POCO and SM8650 outputs were read to a terminal and are committed transcribed. QDC's own
session logs were not pulled before the devices were wiped.
